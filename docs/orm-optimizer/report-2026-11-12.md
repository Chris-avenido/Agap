## Finding details

### 1. function-wrapped OR filters - `applicants.service.ts:374`, `:3422` (Medium, Verified, access layer: raw-pg)

- **What the code does:** logs an applicant in by matching `LOWER(TRIM(COALESCE(email_address, '')))`, the same for `email`, or `UPPER(TRIM(COALESCE(plantilla_item_number, '')))` against one identifier, then sorts by `updated_at`.
- **Plan evidence:** node `Seq Scan on applicants`; estimated rows 530 vs actual 0; actual time 51.5 ms recorded / 51.7 ms warm; shared read 6,495 buffers; table has about 35,513 rows. Parameters: a non-existent email (the miss case, which still scans everything). Plan file `docs/orm-optimizer/plans/applicant-login-lookup.json`.
- **Why it matters:** runs on every login and grows with the table.
- **Fix applied afterwards:** `index_cleanup_migration.sql` section 4 adds three expression indexes (`idx_applicants_login_email_address`, `idx_applicants_login_email`, `idx_applicants_login_plantilla`) matching the query expressions. Re-measured on the same parameters: 51.5 ms to 0.049 ms (7 buffers, no sequential scan). Plan file `docs/orm-optimizer/plans/applicant-login-lookup-after.json`.
- **Other sites in this group:** the same pattern in the reclass login path (`:3422`).

### 2. OR with column cast - `vacancies.service.ts:70` (Medium, Verified, fixed)

- **Plan evidence (old query):** node `Seq Scan on applications`; estimated rows 199 vs actual 71; 6.77 ms recorded / 20.8 ms warm; 2,696 buffers; table about 25,664 rows. Parameter: applicant 512 (71 applications). Plan file `docs/orm-optimizer/plans/vacancies-applied-old.json`.
