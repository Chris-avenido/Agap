# Empathy and copy

## Design thinking loop, mapped to the workflow

| Phase | Workflow step | Output |
| --- | --- | --- |
| Empathize | 3 | Three-line user brief |
| Define | 4 | Primary job in one sentence, one memorable element |
| Ideate (design plan and double review) | 6 | Design plan, reviewed against the generic tells and the craft floor |
| Prototype | 8-10 | Built screens with real copy and all states |
| Test (audit, screenshots, craft floor) | 11 | Audit script, light/dark screenshots at desktop and mobile, craft-floor checklist |

## Understanding users without assuming

- Identify the audience from the project (roles, permissions, page names, existing copy) and from the user's answers.
- Consider device and setting (desktop in an office, phone in the field), connectivity, experience level, and the emotional state of the task (routine, urgent, high-stakes, unfamiliar).
- Do not assume users are designers or analysts. The screen should explain itself.
- If you must ask, ask at most three questions, and make each one answerable in a few words.

## Empathy moves that make an interface feel human

- Say what the screen is for in one plain line near the title.
- Reassure at risky moments: explain what will happen before a destructive or irreversible action, and offer undo.
- Save work and say so ("Saved just now").
- Show progress and what is left.
- Forgive input mistakes and explain the fix next to the field.
- Make the most common task the fastest path.
- Respect people's time: avoid unnecessary confirmations, and remember filters and scope.
- Use a warm, professional greeting only where it helps orientation, never as decoration.
- Explain abbreviations and domain terms where they appear.
- Explain why something is disabled or unavailable.
- Show progress and what is left before the user can finish.
- Show unsaved changes and confirm saves.

## Writing rules

- Name things the way the product's users say them, not how the system is built.
- Sentence case, plain verbs, active voice.
- A button says exactly what it does ("Save changes", not "Submit"). The same action keeps the same name through the whole flow, including its confirmation message.
- Errors say what happened and how to fix it, without apology or blame.
- Empty states say what to do next.
- Review designs with realistic data: long names, large counts, missing values.
- No lorem ipsum, no "John Doe", no filler company names.

## Inclusive checks

- Reading level: short sentences, common words.
- The app's existing language: do not translate unless asked.
- Screen reader labels on icon-only controls, charts and status pills.
- A logical focus order that matches the visual order.
