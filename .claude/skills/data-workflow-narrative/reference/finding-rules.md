# Finding rules (R01 to R14)

This list is a minimum, not a limit. `inventory.mjs` emits **candidates** per rule with a confidence; every candidate needs human-style judgment against the surrounding code before it becomes a finding. Read the cited slice (and the caller, when the rule says so), then confirm, downgrade or discard. Add problems the rules miss.

Severity words: Critical = data silently lost or corrupted on a normal path; High = data lost or request fails on a common path; Medium = lost only in some conditions or only partially; Low = hygiene or unlikely.

| ID | Name | What to look for | Why it matters | How to confirm | Typical severity | Fix-brief pattern |
| --- | --- | --- | --- | --- | --- | --- |
| R01 | Write not awaited | An insert/update/delete (or a call to an async function that writes) used as a statement with no `await`, `return` or `.then`; async `forEach` with writes. | The answer can go back before the save finishes, and a failed save is never reported. | Check the call is not returned or awaited by the caller; check the function is async. | High (Critical if the response says success) | Await the write (or return it); let errors reach the error handler. Test: force the write to fail and expect a non-2xx. |
| R02 | Error swallowed | A `try/catch` around a write whose `catch` only logs/ignores and the handler goes on to send success; `.catch(() => {})` on a write. | The person sees "saved" while nothing was saved. | Read the catch and what is sent after it. | Critical when success is returned | Rethrow or pass to `next(err)`; return an error status. Test: make the write throw, expect an error response. |
| R03 | Response before write | A success response sent (not returned) before a later awaited write in the same flow. | A later failure cannot change the answer already sent. | Check no `return` between the response and the write. | High | Move the response after the awaited write; or return an accepted status (202) if the write is deliberately deferred. |
| R04 | Dropped field | A field the schema accepts (or the client sends) never reaches the insert/update; the Zod object silently strips unknown keys. | Data the person typed disappears without any error. | Compare client payload keys, schema keys and written columns; check for `.strict()` / `.passthrough()`. | High | Add the field to the schema and the write, or remove it from the client; consider `.strict()`. Test: send the field, read it back. |
| R05 | Required column never supplied / wrong mapping | Insert into a table with a NOT NULL column that has no default and is not in the values; dates, numerics or JSON passed in the wrong format. | The insert fails (500) or stores the wrong value. | Check the column in the schema and the full values object (including spreads and defaults in a trigger). | High | Supply the value (or add a default through a migration proposal). Test: post a minimal valid body and expect 2xx. |
| R06 | Silent no-op | An update/delete by key that does not read `returning` or the affected row count, and no earlier lookup. | A missing record still gives success, so a mistaken id looks saved. | Check whether a prior select proves the row exists, or the service treats "0 rows" as fine on purpose. | Medium (High with an id in the path) | Use `returning()` or check the count; return 404 when nothing matched. |
| R07 | Missing transaction / wrong executor | Related writes to two or more tables outside one transaction; a write using `db` instead of `tx` inside a transaction callback. | A failure between writes leaves half-saved data; a write on `db` escapes the transaction and is not rolled back. | List the writes in order; decide if a partial result is harmful. | High (wrong executor) / Medium | Wrap in one transaction and use `tx` for every write inside. Test: fail the second write, expect the first rolled back. |
| R08 | Buffered but never flushed | Data pushed to Redis or a queue with no worker/consumer reading it, or a TTL short enough to expire before processing. | Data accepted by the server never reaches the database. | Search the whole repo for the consumer, check queue names match and the worker is started by a process. | Critical | Add or start the consumer; align queue names; remove or lengthen the TTL. |
| R09 | Frontend/backend mismatch | A client call to a route that does not exist, with the wrong verb, or sending keys the server rejects or ignores. | The screen looks fine but the save request fails or is ignored. | Compare verb + path in the inventory; compare payload keys with the schema. | High | Align client call and route (verb, path, keys) in the shared types. |
| R10 | Mutation that writes nothing | POST/PUT/PATCH/DELETE whose whole call graph has no write and no enqueue; stubs, TODOs or only logging. | The person believes it saved. | Read the handler; check it is not a pure check, calculation or login. | High if a stub, else Low | Implement the write or change the route to a read/verb that matches its purpose. |
| R11 | Unhandled conflict | Insert into a table with a unique constraint with no `onConflict*` and no duplicate handling (500 on duplicates); an upsert whose conflict target is not a unique/primary key set of the table. | Retries and double-submits produce errors; a wrong target fails or duplicates. | Compare the conflict target with the table's unique/primary key sets. | Medium | Add `onConflictDoUpdate/DoNothing` with the correct target, or map the unique violation (23505) to 409. |
| R12 | Partial writes in loops | Per-row awaited writes in a loop (or parallel map) with no transaction and no per-row failure reporting. | A failure on row 7 leaves rows 1-6 saved and the person told nothing useful. | Check for a surrounding transaction or per-row results in the response. | Medium | Batch the rows in one statement inside a transaction, or report which rows failed. |
| R13 | Read-after-write inconsistency | A handler reads from a cache or replica right after writing; cached reads with no invalidation after writes. | The screen shows the old data after a successful save. | Check what the read source is and whether writes invalidate it. | Medium | Read from the primary after writing, or invalidate/update the cache in the same flow. |
| R14 | Validation gap | A mutating route that reads `req.body` with no schema; a schema looser than the column (no max length for a limited column, plain string for a uuid or enum). | Bad data is saved, or the database rejects it with a 500 instead of a clear message. | Compare schema leaf rules with the column type and limits. | Medium | Add or tighten the shared schema to match the column. |

## False-positive examples (two per rule)

- **R01**: (a) the write sits inside `Promise.all([...])` that is awaited by the caller; (b) the function returns the write's promise and every caller awaits it.
- **R02**: (a) the catch rethrows a typed error or calls `next(err)`; (b) the catch handles one expected case (for example a duplicate key mapped to 409) and rethrows everything else.
- **R03**: (a) the early response is inside an `if` that returns (a validation failure), not on the success path; (b) the "write" after the response is a log or metrics call, not a database write.
- **R04**: (a) the schema key is consumed by name and used to compute a different column; (b) the handler passes the whole validated object to the insert, so every key is written.
- **R05**: (a) the column is filled by a database trigger or generated expression; (b) the value arrives through a spread of an object that includes the column.
- **R06**: (a) an earlier select already proved the row exists and ownership; (b) the operation is idempotent by design (delete of an already-gone row is success).
- **R07**: (a) the second table is written by a database trigger inside the same statement; (b) the two writes are independent and a partial result is harmless (an audit row).
- **R08**: (a) the consumer lives in a separate worker process started by PM2 or a script (check the process list); (b) the TTL is a cache TTL for reads, not a buffer for writes.
- **R09**: (a) the client call is to a third-party service, not this backend; (b) the extra key is a header-equivalent consumed by a middleware.
- **R10**: (a) the endpoint only validates or previews and is meant to write nothing; (b) the write happens in a background worker the inventory lists as the consumer.
- **R11**: (a) the table's only unique constraint is a primary key generated by the database, so duplicates cannot occur; (b) a surrounding `try/catch` maps code 23505 to a 409.
- **R12**: (a) the loop is already inside one transaction and the failure aborts all rows; (b) the loop is over at most two or three fixed items.
- **R13**: (a) the cached value is for a different, unrelated read; (b) the write clears the cache key before the read.
- **R14**: (a) validation is done by a shared middleware earlier on the router (`router.use(validate...)`); (b) the schema is stricter than the column, which is allowed.
