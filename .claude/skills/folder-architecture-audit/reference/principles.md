# Principles (heuristics, not laws)

- **Why structure matters to agents.** An agent's context window is a fixed attention budget. Loading many unrelated files dilutes attention, and similar-looking but irrelevant code (distractors) can mislead a model. Smaller, focused context generally beats loading everything. This is a strong tendency, not a guarantee. Never claim "zero regression" or "mathematical certainty" in the report.
- **Colocate by feature, not by technical layer.** Backend: vertical slices, where one feature's route, validation, handler and data access live together (Express: `features/<feature>/{routes,handlers,schemas,queries}` or one focused folder per use case). Frontend: feature-sliced layers `app > pages > widgets > features > entities > shared`; a module imports only from layers below, slices on one layer do not import each other, and each slice exposes a public API through `index.ts`.
- **Rule of Three.** Extract to a shared folder only when three or more features need the same code. Small local duplication beats a wrong shared abstraction.
- **Cross-feature communication.** Features do not import each other's internals. Go through the owning feature's public module, or use events or queues for asynchronous workflows.
- **Deterministic enforcement beats convention.** Boundaries checked by tools (`eslint-plugin-boundaries`, `dependency-cruiser`, `import/no-cycle`, architecture tests, TypeScript project references) survive agent-driven change; prose conventions do not. Violations should fail inside the agent's own loop (lint or `ci-gate`) so it self-corrects.
- **Context-file layering.** `AGENTS.md` (vendor-neutral, always loaded, about 150 lines or fewer, only hard constraints, commands and non-obvious decisions), thin tool-specific files (`CLAUDE.md`, `.cursor/rules`), and `SKILL.md` folders for on-demand procedures. Put the most important rules at the top: models attend most to the start and end of long inputs. Avoid generic advice such as "write clean code". A nested `AGENTS.md` per app in a monorepo is recommended.
- **File size.** Files over about 500 lines carry unrelated logic and cost many tokens per read. Over 1000 is a strong smell; over 2000 is severe.
- **Navigability aids.** A repo map (each top-level module, its purpose, its public entry point), predictable names, barrel `index.ts` used only as public APIs, and a single-command verification (`typecheck`, `lint`, `test`, `ci`).
- **Debuggability.** One obvious place per concern for logging, error handling, request correlation, config and health or diagnostic endpoints. Tests colocated or mirrored predictably so an agent finds the test for a file in one step.
- **Project-fit calibration.** Do not penalize small repos (under roughly 50 source files) for lacking full layering. Do not recommend a pattern without citing the specific pain it removes in this repo. Prefer the smallest change that removes the pain. Respect decisions recorded in the repo's `AGENTS.md` or `CLAUDE.md` (for example an intentional `apps/backend`, `apps/frontend` and shared split) and judge against those goals, not a generic template.
- **Limits of the source research.** The research behind this skill was written mostly around .NET examples and contains strong claims. Translate the ideas to Node/Express/React/Drizzle and state uncertainty honestly.

## Notes on inventory metrics
- Deep imports are counted only into feature-classified module folders (not `services/`, `components/` and similar technical folders), and only within one workspace.
- `resolveRate` is best-effort static analysis. Routers registered through unusual patterns show as unresolved even when they are mounted; say so rather than over-penalize.
- Footprint is a static import walk to depth 6 and overstates what an agent really needs when barrels pull in unrelated modules. Treat it as a relative measure.
